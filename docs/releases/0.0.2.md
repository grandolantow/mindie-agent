# MindIE Agent `0.0.2` 版本发布记录

[English](0.0.2.en.md) · [返回文档中心](../README.md)

当前为发布候选记录，正式状态以 GitHub Release 与下述精确源码清单为准。

主产品与 Codex、Claude Code、Kimi Code、DSH 四个插件统一为 `0.0.2`。共享组件保留独立版本序列；`mindie-bench` 为 `0.2.0`，其代码仓库已公开。本次发布以重构后的业务正确性、实际安装依赖闭环和持续 benchmark 交付为重点。

## 主要修复

- **远端执行与资源协调**：持久作业控制、握手和多阶段 SSH 诊断遵循同一调用预算；提交任务时读取当前 Git 身份，避免缓存旧源码身份。保留已经完成的远端结果，显式区分失败和不确定的外部写入。
- **知识与授权**：修复授权迁移、Windows DPAPI 上下文保护和并发授权更新；保留此前正式补丁的后台服务所有权、任务退役与 Git 解析修复。
- **统一贡献与故障上报**：知识共享与产品故障上报使用同一个贡献选择。修复 DSH 的上报配置路径错位；故障记录、队列和发送前直接检查同一授权修订，开启时准备真实后台服务，关闭后停止两条外发链路。GitHub 暂时不可用不会把尚未发送的故障永久丢弃。
- **宿主进程边界**：摘要调用为身份校验、模型调用和进程回收分别保留预算；DSH 安装超时回收实际进程树，缺失用量仍报告未知，删除通过删配置后重试来掩盖错误的路径。
- **Windows 安装**：Codex 缩短新运行环境的目录标识，保留回执中的完整身份；修复默认用户路径下依赖文件超过传统 Windows 路径限制的问题。Kimi 的原生 Windows 环境要求 Python 3.12 或以上，安装优先使用 3.13。
- **共享状态归属**：删除三个插件的诊断 fallback 与 Kimi 的授权 bootstrap 副本，复用共享组件；共享运行时不可用时明确报告，保留已有授权与原始业务结果。
- **冷启动与后续更新**：Claude Code 串行准备首次状态，已就绪的 MCP 不再等待可选维护的独占锁；维护超时如实返回未完成。Kimi 通过共享选择器匹配正式 Release、宿主兼容声明和精确标签源码。DSH 摘要 worker 安装到持久数据目录，移走安装 checkout 后仍可运行。
- **Linux benchmark 沙箱**：支持 uv 托管解释器的同一运行时别名，继续隔离未授权文件和宿主回环网络；原生 Unix gateway 的测试沿真实 relay 路径验证。

## 验收与测量边界

| 层次 | 本次证据 | 能说明的范围 |
| --- | --- | --- |
| 本地与跨平台 CI | 各仓的单元、组件、进程边界及打包测试；宿主插件分别运行 Linux、macOS、Windows 合同测试 | 具体代码与安装契约；不等于全部真实宿主流程通过 |
| A2/A3 实机集成 | remote-dev 4 项及 8 个子场景、Knowledge 1 项、coordinator 4 项、npu-top 3 项全部通过 | 隔离状态目录下的探测、执行、知识闭环与协调；未占用或停止已有 NPU 工作负载 |
| 原生宿主 | macOS Codex 0.153.4、Claude Code 2.1.269、DSH 0.2.0-rc.2 的局部原生回路；Windows/WSL 安装、MCP 和后台采集按实际成功范围记录 | 本地测试 provider 与公开合成对话；本轮未把付费模型调用作为验收前置 |
| 发布 benchmark | 十仓各自固定 CPU workload，5 次重复，发布原始数值样本、单位、环境、源码与状态 | 当前版本基线；不据此声称 NPU 性能提升或 Agent 提效百分比 |

最终组合的实机测试用时：remote-dev 51.31 秒、Knowledge 6.34 秒、coordinator 22.19 秒、npu-top 14.30 秒。remote-dev 高于测试架构中 Tier 2 的 25 秒目标；结果通过与耗时目标未达成分别记录。

本轮实测发现 A3 `.154` 已处于空闲状态，旧测试要求至少有一个忙碌设备与进程，因此首次结果为 2 项通过、1 项失败。直接读取 `npu-smi` 确认硬件确实无负载后，测试改为核对实时快照、双 Die 映射及 busy 汇总的一致性，再次三项全部通过；没有启动负载来满足断言。这项测试契约修正随 `npu-top 0.1.9` 交付，已发布的 `0.1.8` 保留。

Windows 独立验收机在真实普通桌面 token 下，通过正式 `pythonw.exe` 与 Task Scheduler 完成 Stop 事件回放、采集、脱敏和素材整理，约 6.5 秒，未调用模型。该结果验证组件后台链路，不冒充宿主模型实际生成的一次完整对话。Codex 默认安装目录等长布局验证了真实依赖安装、最长 Anthropic 模块与 LangSmith 导入，以及重复启动复用同一有效回执。

Claude Code 在全新原生 Windows 配置下 46.077 秒完成初始化，两路 MCP 分别在 17.328 秒与 23.208 秒内连接，保留宿主原有 30 秒连接预算。可选 feed 同步超过 20 秒预算，回执明确记录 `maintenance incomplete`；已连接工具保持可用，模型调用为零。

Kimi 在 macOS 2.2.0 的隔离配置中完成 `0.0.1` 到 `0.0.2` 的原生升级：固定源码获取、新运行环境构建、原生 API 安装与回读、原子切换均实际执行，第二次检查保持当前绑定不变。该验证使用受控本地 Release 目录，不冒充已公开的 GitHub `0.0.2` 升级。Windows Kimi 2.1.1 与 macOS 2.2.0 另行读取官方目录，验证兼容性筛选与不降级行为。

最终 A2/A3 批次使用非 editable 安装的 Knowledge `4e32830`、remote-dev `a664922`、coordinator `daf7fa3` 与 npu-top `9bbf6de`，共享 diagnostics `1b5a0ee`；Git 安装身份或安装源码与对应 HEAD 的逐文件比对已核实。此前 Windows/WSL 采集使用 Knowledge `b2c59a7`，Claude Code 前一批冷启动使用 `8d9eab1`。最终统一贡献授权与 reporter 生命周期另有下述原生验收；旧宿主记录不冒充最终提交的完整逐字节重装。

### 统一开关的真实故障上报

在隔离 profile 中，从 Git 精确提交非 editable 安装 Knowledge `4e32830` 和 diagnostics `1b5a0ee`，显式开启统一贡献选择后，macOS 原生 launchd reporter 自动创建了公开合成测试 [Issue #243](https://github.com/mindie-agent/mindie-agent/issues/243)。这次外部写入由后台 worker 完成，没有用测试脚本直接代发 Issue。

回读确认 Issue 包含 diagnostics `0.4.3` 和完整提交 SHA，排除了私有测试标记、原始错误文本及本机目录。重复故障由同一 worker 消费，持久队列仍只有一条已发布记录。开启前和关闭后的故障仅本地记录，不附带上传授权；关闭会使知识贡献与诊断发布使用的同一选择失效。验收后移除隔离原生服务，确认服务已不存在。

验收脚本的第一次去重检查将事件字段误写为 `incident_id`，实际事件使用 `operation_id`；修正检查后在原队列继续验证，没有重放已完成的外部写入。该夹具失败与产品投递结果分别保留。

Windows 4090 使用普通桌面 token（`TokenElevation=0`）经 Task Scheduler 启动同一精确安装组合。其常驻 worker 消费相同公开合成故障，通过 GitHub 只读查重关联到 Issue #243，没有创建第二个 Issue。

已有安装的 `disabled`、`later` 或 `read-only` 保持关闭。旧版仅知识贡献的 `contribute` 若没有统一授权修订，也不会因升级而默默开始上传诊断；用户通过同一个贡献入口明确开启一次即可。配置已写入与后台 worker 已运行分别报告，认证、网络或服务启动失败不能显示为上报成功。关闭阻止后续发送，不撤销此前已经完成的公开写入。

## 每次发布随附 benchmark

每个代码仓的 Tag 发布流程固定执行：源码与版本检查、实际依赖安装、第一方依赖正式发布核验、本地合同测试、benchmark、打包与校验。任何必需场景失败、缺失或不确定都会阻止发布。

组件 Release 随软件包提供 `benchmark-results.json`、`benchmark-results.md`、`benchmark-SHA256SUMS` 与覆盖全部公开附件的 `SHA256SUMS`。主产品提供十仓聚合报告、原始清单和 `product-release-provenance.json`；公共附件不携带私有日志或用户对话。

本轮首次发布的 diagnostics、remote-dev、npu-top 校验清单曾多列一个没有上传的构建目录 `.gitignore`。已只修正 `SHA256SUMS` 并在各 Release 说明更正；标签、软件包、benchmark 报告及其摘要均未改变。共享发布流程已修复该问题。

Knowledge `v0.12.0` 与 coordinator `v0.5.0` 的候选发布分别被 benchmark 数据契约和 Python 可选测试扩展问题阻止；两个标签保留，未创建正式 Release。修复后先发布 `v0.12.1` 与 `v0.5.1`，本次统一开关最终组合再前进到 `v0.12.2` 与 `v0.5.2`；没有移动失败候选的标签或将失败改记为通过。

## DSH 同版本更新

DSH 按产品决定保持 `0.0.2`。此前 `0.0.2` 的源码为 `828c375d1f546ed653250526465b8075c1691390`；本次配套源码以组件清单为准。

旧版 updater 只选择高于当前版本号的版本，已安装旧 `0.0.2` 的用户不会自动收到同版本内容更新。此类安装需要一次显式刷新运行环境及 DSH 插件包，并重启整个 DSH 进程；已有授权和知识数据保留。按[同版本刷新步骤](https://github.com/mindie-agent/mindie-agent-dsh/blob/main/docs/same-version-refresh.md)使用精确源码 SHA，避免同名标签的客户端缓存。后续更高版本继续走正常更新通道。

## 已知边界

- Lenovo Windows 验收机的应用控制策略阻止 `pythonw.exe` 执行，返回 WinError 4551；没有修改或绕过机器策略。该主机上的后台采集不计为通过。
- Windows 的普通桌面 token 已验收。管理员提升的宿主可能创建普通用户后台任务无权读取的私有状态目录；本次不声明提升权限宿主与普通权限后台任务的混合运行已受支持，也不通过修改 ACL 或提权绕过。
- 全部源码测试、宿主局部原生验收、A2/A3 集成和 CPU 基线分别记录；没有把旧版本完整宿主矩阵转记为 `0.0.2` 的新证据。
- 知识、远端开发与宿主插件的独立生产力收益仍需要同任务、同环境的对照实验。本次交付的是可复现基线与后续每次发行的常态报告。

# MindIE Agent `0.0.2` 版本发布说明

[English](https://github.com/mindie-agent/mindie-agent/blob/v0.0.2/docs/releases/0.0.2.en.md) · [文档中心](https://github.com/mindie-agent/mindie-agent/blob/v0.0.2/docs/README.md)

本文记录 MindIE Agent `0.0.2` 的功能变更、组件源码清单、分层验收证据、十仓基准测试（Benchmark）及已知边界。正式发行状态以 GitHub Release 及其随附的校验清单为准。

在 `0.0.2` 中，主产品与 OpenAI Codex CLI、Claude Code、Kimi Code、DeepSeek Harness（DSH）四个宿主插件统一为 `0.0.2` 版本；底层共享组件与评测工具 `mindie-bench`（`0.2.0`）保持各自独立的版本序列。本次发布重点收敛了跨组件业务正确性、统一贡献与故障上报授权边界、固定依赖安装闭环，并建立每次 Release 随包交付可复现基准测试的机制。

---

## 一、核心变更

- **统一贡献与故障上报开关**：社区知识共享与工具故障自动上报共用同一个贡献开关（以安装配置中的 `mindie-consent.json` 为唯一权威来源）。显式开启时同步准备知识贡献配置与系统原生后台 reporter 服务；关闭后立即停止知识外发与故障上报两条出站链路，本地诊断日志与远端开发工具不受影响。修复了 DSH 上报配置路径不一致的问题；网络或 GitHub 认证暂时不可用时保留待发队列并延后重试，不因瞬时查询失败永久丢弃故障记录。
- **远端执行与集群协调**：`remote-dev` 的持久作业控制、RPC 握手与多阶段 SSH 诊断纳入独立且自洽的调用超时预算；`coordinator` 提交任务时实时解析当前 Git 源码身份，避免沿用旧缓存。远端命令已执行成功时保留完整业务结果，显式区分执行失败与外部写入状态未知（`unknown`）。
- **知识闭环与授权安全**：修复授权配置迁移、Windows DPAPI 上下文保护与并发授权更新；保留后台服务归属校验、任务退役回收及 Git 凭据解析修复。
- **宿主进程边界与冷启动优化**：
  - **Claude Code**：串行化首次冷启动状态准备，已就绪的 MCP 服务不再阻塞等待可选 feed 同步的独占锁；后台维护超时如实记录为 `maintenance incomplete`，不影响已连接工具使用。
  - **OpenAI Codex CLI**：缩短 Windows 默认用户目录布局下的运行时环境标识（在回执中保留完整身份），解决依赖路径超出传统 Windows 路径长度限制的问题。
  - **Kimi Code CLI**：原生 Windows 环境要求 Python 3.12 及以上（安装优先选择 3.13）；通过共享版本选择器核验正式 Release、宿主兼容区间与精确 Tag 源码。
  - **DeepSeek Harness (DSH)**：摘要 worker 部署至持久化数据目录，移除安装源码临时目录后仍可正常运行；安装超时完整回收子进程树，缺失的 Token 用量如实报告为未知，移除通过删除配置重试来掩盖错误的逻辑。
- **共享组件复用与状态归属**：移除各插件内重复维护的诊断 fallback 与授权 bootstrap 副本，统一直接调用锁定的共享运行时组件；当共享运行时异常时直接显式报错，不篡改已保存的用户授权或原始业务结果。
- **Linux 评测沙箱**：`mindie-bench` 支持 `uv` 托管解释器的同运行时别名，同时继续隔离未授权文件与宿主回环网络；原生 Unix gateway 测试沿真实 relay 路径验证。

### 关键实机验收说明

- **`npu-top 0.1.9` 空闲主机探测契约修正**：本轮实机测试时常备 A3 `.154` 节点处于空闲状态（经直接运行 `npu-smi` 确认无活跃业务进程），而 `0.1.8` 的旧测试断言要求至少存在一个忙碌设备，导致首次运行 2 项通过、1 项失败。我们在不人为拉起假负载迎合测试的前提下，将测试契约修正为校核实时硬件快照、A3 双 Die（`Phy-ID`）映射与 busy 计数的一致性，并发布为 `npu-top v0.1.9`（源码 `9bbf6de590b12fe1109040e0ef86817bd2c5f3e0`），复测三项全部通过。已发布的 `v0.1.8`（`36ae994`）保留原状。
- **Windows 原生环境与长路径验证**：独立 Windows 验收机在普通桌面权限（`TokenElevation=0`）下，通过正式 `pythonw.exe` 与 Task Scheduler 完成 Stop 事件回放、脱敏采集与素材分块（约 6.5 秒，零模型调用），验证了后台组件链路。Codex 在等长默认用户路径布局下通过了真实依赖安装、最长 Anthropic/LangSmith 模块导入与重复启动回执复用测试。Claude Code 在全新 Windows 配置下 46.077 秒完成初始化，两路 MCP 分别在 17.328 秒与 23.208 秒内连接（满足宿主 30 秒预算）；可选 feed 同步超过 20 秒预算时明确记录 `maintenance incomplete`，已连接工具保持可用。
- **Kimi 原生升级筛选验证**：macOS Kimi `2.2.0` 在隔离配置中依托受控本地 Release 目录完成了 `0.0.1 -> 0.0.2` 的固定源码拉取、新环境构建、原生 API 安装回读与原子切换，二次检查保持绑定不变；Windows Kimi `2.1.1` 与 macOS `2.2.0` 另行对官方目录验证了 SemVer 兼容性筛选与防降级逻辑。

### 统一贡献开关与真实故障上报验收

1. **三态严格区分**：系统明确区分**配置已写入**（`mindie-consent.json` 更新）、**后台 worker 已运行**（系统级守护服务就绪）与**外部发布已完成**（GitHub Issue 或 PR 已创建）三个状态。认证缺失、网络断开或后台服务启动失败均直接报错，绝不把“配置保存成功”显示为“已成功上报”。
2. **升级授权兼容边界**：已有安装中的 `disabled`、`later` 或 `read-only` 状态在升级后保持关闭；旧版仅开启知识贡献（`contribute`）但缺少统一授权修订号的配置，升级后**不会**自动获得故障上报权限，需由用户通过统一贡献入口显式开启一次。关闭开关会立即阻止后续知识与诊断外发（不撤销此前已公开的写入）。
3. **macOS 与 Windows 跨平台去重实证**：
   - 在 macOS 隔离配置中从精确提交非 editable 安装 `knowledge`（`4e32830`）与 `diagnostics`（`1b5a0ee`）并显式开启统一贡献开关后，macOS 原生 `launchd` reporter 后台服务自动创建了公开合成故障 [Issue #243](https://github.com/mindie-agent/mindie-agent/issues/243)。回读确认该 Issue 仅包含 `diagnostics 0.4.3`、完整 Commit SHA 与白名单执行元数据，完全排除了私有测试标记、原始报错文本及本机路径；重复故障被同一 worker 消费后去重，持久队列仅保留一条已发布记录。
   - 在 Windows（RTX 4090，普通桌面权限 `TokenElevation=0`）上通过 Task Scheduler 启动同一精确版本组合后，常驻 worker 消费相同合成故障时通过 GitHub 只读查重自动关联至同一 [Issue #243](https://github.com/mindie-agent/mindie-agent/issues/243)，未产生重复提交。
   - 验收完成后，已关闭测试 [Issue #243](https://github.com/mindie-agent/mindie-agent/issues/243) 并清理移除测试注册的系统服务。

## 四、十仓发布基准测试（Release Benchmarks）

从主产品 `0.0.2` 起，每个代码仓在 Tag 发布时均由固定版本的 `mindie-bench` 运行器在干净工作区上执行 `benchmarks/release.json` 中定义的必选工作负载（`5` 次独立重复），并在确认输出正确后随 GitHub Release 自动附上 `benchmark-results.json`、`benchmark-results.md`、`benchmark-SHA256SUMS` 与总 `SHA256SUMS`。主产品 Release 汇总十个代码仓的正式报告、清单与 `product-release-provenance.json`（主仓仅承载文档与架构资产，不单独运行代码基准）。

### 基准测试能证明与不能证明的边界

- **能证明什么**：在固定公开合成输入与干净构建环境下，各组件核心纯逻辑（脱敏、分词、补丁解析、拓扑放置、硬件报文解析、各宿主公开对话投影提取、检索计分）在当前精确源码 SHA 上的业务输出正确性，以及可跨版本纵向对比的单次操作 CPU 耗时基线。
- **不能证明什么**：CPU 微基准测试不包含 SSH 远端网络传输、容器启动或真实 NPU 算子执行，**不能**替代常备 A2/A3 昇腾真机功能验收，也**不能**由本地解析耗时、pytest 运行时长或仓库下载量推导“NPU 算力吞吐提升百分比”或“Agent 端到端研发提效百分比”。端到端任务提效需通过受控对照实验独立评估。

## 五、DSH `0.0.2` 同版本刷新说明

按产品版本对齐决定，`mindie-agent-dsh` 本次保持 `0.0.2` 版本号，对早先发布的旧 `0.0.2`（源码 `828c375d1f546ed653250526465b8075c1691390`）进行单次授权替换，最新配套源码以本文上方组件表与 [`benchmark-manifest.json`](https://github.com/mindie-agent/mindie-agent/blob/v0.0.2/docs/releases/0.0.2/benchmark-manifest.json) 为准。

- **操作方式**：已安装旧版 `0.0.2` 的用户请参照 [`same-version-refresh.md`](https://github.com/mindie-agent/mindie-agent-dsh/blob/main/docs/same-version-refresh.md) 按精确源码 SHA 显式刷新一次共享运行环境（`setup.py`）与 DSH 插件包，并**重启整个 DSH 进程**（避免客户端缓存同名标签）。刷新过程完整保留已有的用户授权与本地知识数据；后续更高版本将继续通过常规通道更新。

## 六、已知限制

- **特定 Windows 机器的应用控制策略限制**：Lenovo Windows 验收机的系统应用控制策略拦截了 `pythonw.exe`（返回 `WinError 4551`）。我们在验收中不修改或绕过机器安全策略，该主机上的后台采集不计为通过。
- **Windows 权限上下文边界**：普通桌面用户权限（`TokenElevation=0`）下的完整后台链路已通过验收。若宿主以管理员提升权限运行，其创建的私有状态目录可能无法被普通权限的计划任务读取；当前版本不声明支持“管理员宿主 + 普通权限后台任务”的混合权限运行模式，也不通过修改 Win32 ACL 或提权绕过该系统边界。
- **证据独立性**：源码合同测试、原生宿主局部回路、常备 A2/A3 实机集成与 CPU 基准测试各自对应独立证据范围；不将历史 `0.0.1` 的宿主测试矩阵转记为 `0.0.2` 的新验收结论。

# 作者自述：关于 MindIE Agent 的架构设计思考与致谢

[English](design-philosophy.en.md) · [返回 `0.1.0` 版本发布说明](../0.1.0.md) · [文档中心](../../README.md)

> **写在前面**：这篇设计自述原本我是想自己动手写的，但由于我已经半年多没有自己亲手写过一行代码和文档了，最终还是决定采用“我口述 + **Gemini 4 Argon** 整理润色”的方式完成。以下是我对 MindIE Agent 整个架构演进、工具与知识飞轮、工程边界以及人机协同的真实思考。

OK，我们来系统聊聊关于 MindIE Agent 整个的设计思路。

准确来说，一开始我是没有现在这个架构想法的。最开始我想做的是一个类似于 `vaws` 的东西——里面可以塞很多很多的 Skill，然后通过内部的一套机制，让不同 Skill 之间的信息可以充分流转。这是我当时去设计和实现 `vaws` 的初衷。在早期面对智能程度还比较低的模型时，这套做法确实取得了比较好的效果，能显著提升不少任务的成功率。

但是随着 GPT-5.5 这一代模型的出现，我发现这种多 Skill 的形式可能并不是一个最优解，甚至我理解它都算不上一个优秀的解法。因为它会给高智商模型带来非常明显的副作用——**它会让模型变得偏执**。

所以在从 5.5 到 5.6 的那段时间里，其实我是没有去用任何 Skill 的。但很快我也发现，“裸奔”同样存在很大的问题：缺失了一部分必备的领域工具和先验以后，模型在某些工程场景下的能力会明显变差。就拿我们日常的昇腾开发来说，我们所有的机器都在远端服务器上，但开发又是在本地；让模型去拉 PD 分离也好、去拉推理服务也好，经常会出现各种环境变量漏设，或者一言不合就重新编译算子，导致拉起一个服务干等几十分钟；再加上本地如果是 Windows，还会碰上万恶的微软 PowerShell 各种字符串转义的深坑；同时，很多像昇腾 A2、A3、A5 的硬件限制和经验，每次都得靠人去口口相传喂给它。

那时候我就一直在思考：**到底怎么样才是对的？** 我理解现在 MindIE Agent 的这套架构，就是我能给出的答案。

---

## 一、破局与定位：为什么砍掉多 Skill、不做重 Harness，只做“像椅子一样无感”的薄 Plugin？

### 1. 为什么传统多 Skill 是一条死胡同？

首先，整个 MindIE Agent 架构是没有传统意义上的多 Skill 的。因为只要你用多 Skill 的形式去承载内容，就一定会撞上一个无法回避的死结：**由于现有开源 Harness（宿主客户端）的机制限制，所有 Skill 的 `name` 和 `description` 都会被强行加载到上下文里面。**

先不谈这部分内容对 Agent 注意力本身的干扰，单说当你有两三百个 Skill 的时候：一方面它会白白占据非常多的上下文窗口；另一方面，这些 Skill 的唤醒是靠自然语言去匹配它的 Description 的。这个机制在很长一段时间里都让我非常困扰——它老是会误命中很多我根本不想让它命中的 Skill。而要解决这个问题，就需要我人工去设计边界、去维护路由。但说实话，我既没有这个精力、也没有这个能力去完成几百个 Skill 的互斥设计与维护，经常是顾得了这个、顾不了那个。与此同时，散落在各个 Skill 里面的脚本工具往往大同小异，存在大量重复性的代码，导致测试也是极其冗余的。

### 2. 为什么基模厂商的 Harness 满身是 Skill，而我们只留唯一一个入口？

讲到这里，大家可能会问一个问题：**为什么所有基模厂商提供的 Harness 都是带一大堆 Plugin、Skill 和 MCP 的，而你却偏偏只用 MCP 加唯一一个入口（`/mindie-agent`）？**

我理解这个问题的本质在于：**基模厂商的 Harness 需要服务于全世界所有的任务领域，而我们不需要。**
当基模厂商要服务所有领域时，它是不可能把所有行业的知识库全部构建起来打包发出去的——那个规模会无限膨胀。所以基模厂商采取的是一种折中的取舍：一方面通过提供官方 Harness 收集用户交互数据，把高频的 Transcript 直接训练进模型的内部参数里；另一方面开放 Skill 和 Plugin 这种扩展槽位，让用户在它未预设的长尾领域里自己写个 Skill 快速实现目标。

但是我们面临的处境和基模厂商完全不同。**我们面对的是一个极其固定、高度聚焦的垂直领域：那就是如何在昇腾 NPU 上优化推理（Inference）性能，提高在固定 SLA 约束下的整体吞吐。** 这个核心目标是恒定且确定的，它不会改变。正因为领域高度聚焦，我们其实没有太多去写 Skill 的必要；而且我们的知识库完全可以控制在一个相对较小的体积下——因为哪怕是把我脑子里的经验完整蒸馏了，实际上也就才几兆（MB），而我理解我的能力其实已经可以覆盖很多模型性能优化的场景了；哪怕未来用的人再多，整个知识库最终可能也就几个 G、撑死几个 G。

更重要的是，随着模型能力的演进，部分内容是会被模型吃掉的；昨天的经验也不一定能够服务于明天，**知识也是会老化的**。所以后续版本的工作，我们会在整个知识飞轮以及**知识老化**上面去做进一步的演进。

### 3. 为什么只做极薄的一层 Plugin，既不自研 Harness，也不做独立 UI？

另一个问题就是：**为什么只做薄薄一层 Plugin，而不自己造一个完整的客户端或 UI？**

这个道理说起来其实非常简单：**因为我没有能力去训练自己的基模。** 我只能去用比如 GPT、Claude、DeepSeek、Kimi 这种第三方厂商提供的服务。在这些模型的上下文管理（Context Management）上面，我是不可能做得比基模厂商更好的——这是一个不争的事实。只要我没有模型训练的能力，我就不可能去做一个大而全的 Harness。但认清这一点后，这同时也是我的优点：我没有基模训练能力，那我非常自然地可以利用这些厂商“基模 + 原厂 Harness”持续迭代优化的成果，我只需要往上面注入工具以及基模所需要扩展的知识即可。

同样，为什么我不做 UI？**准确来讲，其实我是考虑过要不要做个 UI 界面给当前的这个工程的，但是我最终没有去做。** 一方面是我完全不懂前端设计，而且我也不太懂画画，所以我没有这方面的动力；另一方面，我觉得直接用原厂的 Harness 其实是非常享受的一件事情——比如你可以直接拿手机在外面控制 Codex，也可以拿手机控制 Kimi，包括 DeepSeek Harness 其实也是可以远程控制的。只要你装了我们的薄 Plugin，这些原厂自带的便利性全都可以无缝保留，这是我不想舍弃的一个部分。

并且我认为，**一个好的工具它应该是不被人感知的。就像一把椅子——你坐下来的时候，只会下意识地去找到椅子坐上去，而不会去思考怎么操作它。** 所以我希望 MindIE Agent 的使用、安装包括更新都是尽可能无感的。虽然它不可能真的做到像椅子一样让人永远无法感知，但我希望它对用户的负担尽可能最少。**可能有一天我会去给它加上一个界面，以方便大家完成一些配置，但我理解不会是现在。** 我希望整个组件保留极度的克制以及目标的明确——**这个工具只是用来解决昇腾 NPU 上面的 AI Infra 与推理性能优化问题的**，这个核心目标非常清晰且不变。如果哪天我需要别的目标了，我可能会再去写一套新的东西，而不是去修改现在这套东西。

### 4. 将传统 Skill 彻底拆解为“工具”与“知识”两大支柱

基于上面的定位，我的架构解法非常干脆：**对外只保留一个统一入口（`/mindie-agent`），然后把传统 Skill 里面承载的内容做一次彻底的剥离。**

我理解一个 Skill 里面真正蕴含高信息量的事情，拆到底其实也就三件：
1. **第一件是这个 Skill 承载的工具（也就是 Script）**；
2. **第二件是这个 Skill 所承载的硬性知识与前提**——它类似于“公理”一样的东西，比如硬件的物理限制、内存对齐要求、模型的基本结构，是不随人的意志而转移的客观事实；
3. **第三件是这个 Skill 里承载的做事方法**——无论你叫它 Workflow、SOP 还是踩坑经验，本质上都是**“你能通过什么样的方式去把一件事做成”**，只不过有的是预先设计好的流程，有的是历史经历过的参考。

看清这三件事之后，整个系统自然就生长出了两大核心支柱：**一套按“单一职责原则”收敛的标准 MCP 工具集**，以及**一套分级演进的结构化知识飞轮（`L1–L4`）**。

## 二、第一支柱（工具层）：五大核心工程组件，填平本地 Agent 到远端 NPU 的鸿沟

为了把原先散落在各个脚本里的工具彻底收敛，我们围绕昇腾开发的真实痛点打造了五个核心工程组件：

1. **`remote-dev`（远端对等工具集）**：
   这个仓库的设计思路很早就开始了。因为我很久以前就发现，所有 NPU Infra 开发都面临一个核心痛点：**你的 Agent 是部署在本地的，但你的服务是跑在远端服务器上的，而且往往需要从本地同时控制多台机器。** 但市面上所有开源 Harness 的工具都是写给本地用的，这就产生了一个巨大的 Gap——当 Agent 需要操作远端时，它其实是没有趁手工具的，只能每一轮都在无限重复造 SSH 轮子、拼复杂的命令转义，产生大量固定的 Token 开销。
   我的解决思路非常直观：直接参考所有主流 Harness 原生工具的调用方法、入参和返回格式，1:1 实现了一套**只增加一个 `remote_` 前缀、但使用方法和使用习惯完全一致的对等工具**（比如本地调 `read`，读远端只需要调 `remote_read`），并内置了长耗时后台任务托管与断线重连。这样一来，不管底层是什么基模、跑在什么 Harness 上，都能零成本用起来，彻底解决 Agent 没有远程工具可用的困境。
2. **`coordinator`（集群免密、算子缓存与多卡租约管家）**：
   做这个组件的初衷源于三个非常真实的痛点：
   - 第一，每次攻关分配下来的新机器，我都得重新输密码、传公钥、建容器，过程极其繁琐。我就希望把账号密码交给 Agent 之后，它能自动把我机器的公钥配上去，以后全走公钥免密登录。
   - 第二，我实在不希望 Agent 每次改两行 Python 代码跑任务，都去重新编译一遍 `vllm-ascend` 的算子——虽然这个编译慢的现状某种程度上也是由我当年带来的——我希望它在只改 Python 代码时直接复用之前的算子编译产物，而不是每次都去重编一遍 AscendC。于是就有了**多机器编译缓存复用**的功能。
   - 第三，我不希望手头的几个 Subagent 在并发跑任务时互相抢容器、抢卡，所以我们引入了感知硬件物理拓扑（包括专门处理昇腾 A3 一卡双 Die 的 `Phy-ID` 映射防干扰）的 **NPU 与端口租约机制**，并配套了实时监控面板 `npu-top`。
3. **`sim`（`mindie-sim` 四阶段全栈性能仿真）**：
   这个组件逻辑很纯粹：我缺一个专门给 Agent 使用的性能仿真建模工具，而且我需要它具备从**底层的硬件与算子流水（Pipeline）→ 中层的子图结构（Subgraph）→ 模型的整网并行（Net）→ 顶层的推理服务**这四个阶段的全链路 Roofline 仿真建模能力。所以我做了一个专门给 Agent 用的仿真建模组件——当然，实话实说，代码其实是 Agent 自己写的，跟我没什么关系。
4. **`profiler`（`mindie-profiler` 原地性能剖析）**：
   `profiler` 是个很有意思的组件。过去看 Profiling 全靠人肉眼去扒，但说实话，拆 Profiling 是一件极其枯燥乏味、且没有太多技术含量的体力活。虽然导致性能问题的底层原因千千万，但在推理场景下，Profiling Trace 能够反映出来的性能瓶颈现象翻来覆去也就那几个。
   所以我做的事情，就是把我平时快速分析 Profiling 性能现象的经验，以一套非常固定的模板沉淀到了工具里面，让 Agent 可以**直接原地读取原始的 Profiling 数据**完成 Host-Device 关联和跨轮次对比，而不用再去跑笨重的 `torch_npu` 解析，从而大幅提高整个调优流程的效率。
5. **`mindie-bench`（真机端到端评测——飞轮的收口闭环）**：
   这个组件最开始做起来，只是想用来证明一下这个项目的能力；但在做的过程中我发现，它是极其必要的一环。因为如果没有 `mindie-bench`，你根本不知道你的每个版本到底优化了多少，也不知道你这一整套知识机制到底管不管用。它构成了整个系统闭环的锚点：每当新经验沉淀进知识库、准备发布下一个版本时，我们都可以用 `mindie-bench` 在真机上进行系统性的量化检验。

## 三、第二支柱（知识层）：从 `L1–L3` 经验蒸馏到 `L4`（RSI），以及知识的自愈与老化

有了趁手的工具之后，第二大支柱就是如何把“硬性公理”和“做事经验”装进系统里，并且让它越用越聪明。

### 1. `L1–L3` 分级蒸馏：安全带、标准微流程与实战经验

我把自己所有的实战 Transcript、能找到的开源 Skill、社区的 PR 以及相关文档，做了一次统一的蒸馏，自然分成了三层：
- **`L1` 客观公理与底线（`foundation_baseline`）**：比如昇腾 910B / A3 / A5 的硬件规格约束、静态图捕获要求与测量基准。我们在检索引擎里做了严格的**环境条件门禁（Condition Gating）和 `L1` 保底挂载**——哪怕模型搜索的关键词再偏，只要识别出当前机器的芯片型号和仓库条件，对应的 `L1` 硬件底线就会像“安全带”一样自动挂上，优先保障预算不被挤占，绝不会把 A2 的经验错用到 A3 上。
- **`L2` 标准操作规程与微流程（SOP）**：比如写完算子之后，性能验证必须通过“先跑 After、再跑 Before、再跑 Before、再跑 After”这种 **ABBA 交错测试**来消除机器热噪；再比如先缩小规模、确认在局部算子或子图取得真实收益，然后再上整网验证；包括精度问题定界、性能问题剖析的这类标准小流程。
- **`L3` 具体排障与调优经验（Workflow）**：比如在哪个版本、什么场景下，利用什么方法解决了什么具体问题。同时我们还把知识的“层级（`L1–L4`）”和“证据强度（硬件规范 / 复现实测 / 单次观察假设）”做了独立标记，避免模型把单次巧合当成铁律。

### 2. 从 `L3` 到 `L4`（RSI 独立探索）：打破历史先验的思维定势

如果只做到 `L1–L3`，大家看下来会发现它和开源社区的 Hermes 等 Agent 理念其实是一致的——本质上都是对历史经验的蒸馏与复用。

**但只有 `L1–L3` 是绝对不够的，因为它一定会牺牲掉顶尖模型本身的探索能力。** 当你把历史先验（尤其是 `L3` 的具体经验）喂给模型之后，模型就会顺着你的先验快速收敛。在常规问题上这是好事，但在未知的新问题或极限优化上，这是我们最不希望看到的思维定势。

所以在 `L1–L3` 的基础之上，我引入了 **`L4` 这一层（独立探索模式，`mode="explore"`）**，理念源自 **RSI（递归自我改进）**。我对 RSI 本质的理解，其实就是**“带限定边界的暴力搜索”**——这种爆搜如果让人手写代码去试，代价是不可承受的；但由于 Agent 极高的执行效率，这个爆搜的代价相比于人去做已经变得非常低了。

因此我在系统里加入了一个关键机制：当 Agent 面临无法用 `L3` 既有经验解决的问题、或者离硬件 Roofline 还有明显差距时，它会**切换上下文进入 `L4` 模式**。在这个模式下，系统会自动**物理屏蔽掉 `L3` 的常规经验**以避免先验污染，只挂载 `L1` 硬件约束、`L2` 实测瓶颈、`L4` 候选代码变换（Mutator）以及**已证实无效的避坑清单（`conditional_avoid`）**，在隔离环境里严格跑完“CPU 并行编译 → NPU 串行计时 → 四步验证（编译、精度、性能、留一法消融 Ablation）”，从而彻底避免带着旧先验在死胡同里浪费时间。

### 3. 工程运维与演进取舍：无感自动更新、故障自闭环与隐私安全的知识飞轮

在日常运行与知识演进的闭环上，我们也做了几个非常明确的工程取舍：
- **后台无感自动更新**：准确来讲，整个组件的迭代速度是非常快的，基本处于一个“我有新内容验证好我就直接发”的状态。如果让用户每天手动去更新，其实是一件很不舒服的事；但我又绝不希望用户留在旧版本里，被我们已经知道并修掉的 Bug 反复拷打，所以我们做了后台空闲时的静默自动更新。
- **故障自动检测与修复 Bot（`diagnostics`）**：针对用户运行时候遇到的问题，我们也做了专门的故障检测组件。如果用户同意开启社区贡献，当运行 MindIE Agent 遇到内部故障时，它就会自动脱敏上报 Issue，而我这边会有一个后台 Bot 去专门接单解决这个问题——这既解决了运维的难题，也省去了让用户自己排查和提单的麻烦。
- **双保险隐私脱敏的知识飞轮**：关于知识飞轮的闭环，因为我是绝对不可能去收集用户的原始数据的，所有经验沉淀都通过会话结束时的 `Stop` Hook，在本地先经过**确定性正则 + Gitleaks 双重隐私脱敏**（剔除内网 IP、机器路径与密钥凭据），且一次授权长期无感生效。用这个项目唯一的代价，就是在任务结尾的时候会多花一点点 Token；但换来的福利，是可以享受到所有人的集体智慧——这也是我做这个项目的初衷：集大家所有人的智慧去强化 Agent 的能力。
- **基于真实 Transcript 强监督信号的自纠错（以及为什么不需要重度人工维护）**：在我的设想里，这套知识体系其实不太需要人去重度维护——虽然它肯定还是需要人维护的。因为在我的理解里，当真实任务发生时，**人与 Agent 对话的 Transcript 本身就已经是一个非常强的监督信号了**。这个强信号能够被知识库吸收，无论它是对的还是错的，都有后续的真实任务去确认：如果是对的，就会被持续采用和加固；如果是错的，后续遇到它的 Agent 跑不通，一定会帮它纠正过来。除了硬件的物理参数，我理解**没有东西是永恒不变的，只有变化是不变的**，所以也不需要人去死板预设太多规则，因为人也是会犯错的。我们人工维护主要的工作，其实就是吸收优秀的实战经验，或者针对真实的业务痛点去发现和打磨新的功能与工具。

## 四、控制哲学与人机协同：弱状态机、高精地图，以及“编译器 vs. 许愿机”

工具和知识飞轮都齐了，最后一个核心问题是：**在运行时，我们应该怎么控制 Agent？人又应该站在什么位置？**

### 1. 为什么坚持“弱状态机”？

大家仔细看架构会发现，除了从 `L3` 切 `L4` 进入 RSI 探索模式那一下之外，整个 MindIE Agent 是没有用很强的代码状态机去控制 Workflow 的。

因为我一直认为，**Agent 和传统软件的根本区别在于：软件只能解决预设好的“封闭世界问题”（固定输入 → 固定输出），而 Agent 最大的魅力在于它能解决“开放世界问题”。** 无论学术界怎么争论，我个人认为前沿模型是有创造力的，而且在绝大部分任务上的智商显著高于我。如果用我写死的 Workflow 或状态机去框住它，根本无法发挥它的真正能力。在解决任务的过程中，我实际上充当的是 **PM（产品经理）** 的角色——我把任务派发给它，由它去直面具体的问题，我的业务经验只能给它提供参考。所以除了帮它切换上下文以消除旧经验带来的先验污染之外，我不会用强状态控制去束缚它。

### 2. 智能驾驶隐喻：`L3` 高精地图导航 vs. `L4` 人类驾驶员协同

不用强状态机束缚它，并不代表整个系统就已经实现了“无人托管的全自动演进”。恰恰相反，**人的持续纠偏在整个过程中依然至关重要。**

我理解我做的整个系统，就像是造了一辆带智能驾驶功能的车：
- **`L3` 就像是自动驾驶里的“高精地图导航”**：在别人已经跑通的熟路上，你可以顺着前人的高精地图，极快地收敛到他的目的地；
- 但现实研发中，你的目的地往往和前人不一样（比如 0-day 新模型或全新算子结构）。一旦驶出高精地图覆盖区，系统就切换到 **`L4` 辅助驾驶模式**。这时候，依然需要一位经验丰富的人类工程师介入，与模型一起迭代纠偏；而当人和模型共同趟出一条新路之后，这次突破又会被再次蒸馏沉淀下来，创造出新的 `L3` 或 `L4` 高精地图。

### 3. 这个项目会取代我吗？——人不可替代的三个关键位置

讲到人机协同，其实我也认真想过一个问题：**我甚至担心过这个项目会不会把我给取代了？** 因为准确来讲，我目前脑子里所有的知识，基本都已经蒸馏在这个项目的知识库（或者说经验库）里面了。

但想明白之后我发现，MindIE Agent 本质上并不是一辆能够完全脱离人类驾驶员的车。在未来的演进中，人始终处在一个不可替代的关键位置，有**三件最核心的事**是必须由人来完成的：

1. **第一件事，是人需要向 Agent 清楚地阐述目标，并补齐它不知道的业务背景、前置依赖与隐性约束。**
   这个能力是 Agent 永远无法自己具备的——因为你的服务对象不可能是另一个 Agent；你的客户要么是你的领导，要么是一线团队，要么是外部真实的客户。只有人才能理解真实世界里的诉求，把那些没写在代码里的业务上下文转化成清晰的目标。
2. **第二件事，是切换到 `L4`（RSI 探索模式）之后的方向盘纠偏。**
   进入 RSI 模式后，虽然系统有一套机制能让模型比常规盲搜收敛得更快，但**真正决定收敛速度上限的，依然是人**。这就需要深度的“人机协作”——在未知的路况下，一个优秀的驾驶员极其重要，你需要在关键的路口握住方向盘打一把方向，及时叫停走偏的试探，让它始终朝着正确的道路行驶。
3. **第三件事，也是最关键的一件事：人必须对 Agent 的最终产物负责——在真正的商用代码上，你要把 Agent 当成“编译器”，而不是“许愿机”。**
   这个道理其实非常直观：如果你不参与、不了解 Agent 思考和推进的过程，那么当它一口气给你吐出几万行代码的时候，你甚至连它到底干了什么都搞不清楚。
   现在业界比较主流的一种做法，是让 Agent 在开始前先写详细的 Spec，过程中写过程文档，结束时再写一份长篇大论的总结报告。但说实话，当它给你生成大几万字充满专业细节的文档时，我不认为真的有人会把它全部读完——至少我是不看的，我既没有这个精力，也没有这个能力去把几万字的生成文档逐字看完。
   那我怎么去控制我的 Agent、怎么对最终交付的产物负责？我的核心观点是：**当你清楚地知道它的思维正在朝什么方向发展时，你自然而然就知道它的产物是不是你预期的样子。**
   在真正的商用工程代码上，我理解 **Agent 扮演的更多是一个“编译器（Compiler）”的角色——它负责把你脑海里已经想明白的思路和架构“编译”成代码；而不是一个“许愿机（Wishing Machine）”——让你闭着眼睛把模糊的想法许愿出来。** 这两者有着本质的区别：只有当你把 Agent 当“编译器”用的时候，你的思维和它的执行是同频的，你才可能对最终交付的代码交出一个负责任的结果；如果你把它当“许愿机”用，哪怕它在开始时给了你再详细的 Spec、过程中留了再完整的过程文档、结束时交了再漂亮的总结报告，本质上你依然不知道它到底干了什么。

所以这就是我对人与 Agent 关系的思考：**Agent 无法取代人，或者至少，它永远无法完全取代一个清醒的驾驶员。**

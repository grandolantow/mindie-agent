## 二、会话使用方式：确定性工具默认就绪，知识功能按会话显式启用

在一个新会话中，已配置的确定性工程工具默认可用，包括远端开发（`remote-dev`）、设备探测（`npu-top`）、资源租约与拓扑协调（`coordinator`）、性能分析（`profiler`）、仿真计算（`sim`）和事实状态查询（`diagnostics`）。它们继续遵守各自的权限与安全配置。

需要知识检索或经验复用时，在当前会话手动输入 `/mindie-agent`（Codex 同时支持 `$mindie-agent` 与带插件命名空间的入口）。启用一次后，同一会话的后续轮次会沿用该授权，直到显式执行 `/mindie-agent off` 停用。新会话、分支会话（Fork）和子代理（Subagent）均保持默认静默，需要各自显式启用。

这项会话授权覆盖整个知识闭环：检索、解释、反馈、蒸馏、同步，以及后台经验采集。公开或跨范围经验贡献仍需满足已保存的贡献同意与项目范围配置；安装插件或开启贡献同意本身不会自动启用会话知识功能。

未启用的会话不会收到知识 Skill 正文、知识引导或缺少授权的主动提醒。如果模型在未启用会话中意外调用了知识工具，运行时会在启动知识服务、读取本地语料或采集对话内容前直接在共享 Admission 门禁拒绝调用；普通确定性工具照常工作。

## 三、核心修复与工程改进

### 1. 会话显式知识门禁、整包 Token 预算估算与宿主探索结果原样透传（`knowledge` & 四端插件）

- **显式入口与共享 Admission 门禁对齐**：移除旧的隐式或自动关联授权路径；修复 Codex 手动入口后的知识准备流程，以及 DSH 插件重载后同一会话已授予权限的恢复逻辑。四个宿主插件统一回归了未启用、已启用、后续轮次、新会话隔离、显式撤销与后台采集路径。
- **整包交付 Token 预算估算与完整探索前提（`knowledge #97` / `#100`）**：`mindie_knowledge/graded/budget.py` 通过 `response_token_estimate` 对最终交付的 `query`、`explain` 与 `mixed_query` 响应载荷（含 `exploration_context` 及 `usage` 块，`budget_scope = WHOLE_DELIVERY_SCOPE`）实施统一的整包 Token 预算估算与预算一致性控制（而非依赖特定大模型的精确 Tokenizer 计数）。当固定协议外包估算值已超出请求预算时，如实返回 `budget_met=False` 与 `minimum_tokens`；单条 `explain` 合入兼容视图后通过 `reconcile_budget_truth` 重新判定预算估算状态；探索模式下保留未截断的完整前提正文，按 `L4 -> L2 -> L1` 顺序整条移出超预算单元至 `excluded_units`（并在 `subagent_fact_pack.prompt_brief` 中列出待按需读取的 `ref`），同时调用 `refresh_exploration_mounts` 刷新视图；导航视图裁剪时仅剥离预览 `excerpt` 文本并标 `excerpt_omitted=True`，保留旧材料引用以确保 `related_next` 分页游标可达。
- **单事务去重交付记账与混合检索源索引绑定（`knowledge #97` / `#99`）**：`observe_delivered` 严格按最终裁剪后的交付集合记账——同一 `(unit_id, revision)` 同时出现在结果、卡片、基础卡片或 `exploration_context.mounted_units` 中只计一次，在单个 SQLite 写事务（`_write_txn`）内批量写入；`mixed_query` 通过 `defer_delivery=True` 保留组装子页时的同一个内存 `RoutingIndex` 实例完成预算裁剪与交付记账，避免并发安装新知识流时再次读取索引发生版本漂移；继承前提仅登记为可读，不计作独立交付。
- **共享组件正式 Release 独立发现与旁路隔离环境准备（`knowledge #101`，提交 `0e4123d` / `7357417`）**：新增 `component_releases.py`、`component_runtime.py`、`runtime_inventory.py` 与 `release_http.py`，支持各宿主更新器直接从官方组件仓库发现正式 GitHub Release，校验证书、不可变 Tag SHA、`pyproject.toml` 与 `benchmark-results.json` 后在旁路独立 `uv` 环境中构建锁定运行时，且绝不主动启动知识后台服务或改变 `/mindie-agent` 手动会话启用契约（本地全量 `1555 passed, 22 skipped, 3 deselected, 3 subtests`，组件更新定向 `58 passed`，三类 CI 已通过）。
- **四端宿主插件探索结果原样透传（Codex `#58`、CC `#43`、Kimi `#46`、DSH `#16`）**：四个宿主插件仅负责 MCP 参数校验、宿主身份与协议适配，直接原样透传知识引擎已生成的探索结果（不再二次剥离 L3、重建事实包或二次归一化 `conditional_avoid`），同时完整保留手动 `/mindie-agent` 会话启用门禁。
- **已验证测试事实**：知识预算、去重交付与手动门禁跨 8 个模块联合回归 **`105 passed, 1 skipped`（`13.02s`）**；四端宿主插件基于正式 `knowledge 0.13.2` 锁的定向回归全部通过（Codex `45 passed + 5 subtests`、CC `32 passed + 16 subtests`、Kimi `30 passed + 6 subtests`、DSH `39 passed + 4 subtests`）。

### 2. 远端 SSH 清理诊断保留、HBM 遥测一致性与实测容量准入（`remote-dev 0.10.6` & `coordinator 0.6.3` 候选）

- **SSH 流式与转发清理错误不掩盖主异常（`remote-dev #43`）**：`ssh_stream.py` 与 `ssh_forward.py`（`LocalForward.__exit__`）在主操作已抛出异常且本地清理也失败时，通过 `record_cleanup_failure(primary_error, cleanup_error)` 将清理失败记录到主异常的 `cleanup_error` 字段与异常附注中并重新抛出主异常（修复模块拆分后误用未绑定 `transport` 导致 `NameError` 覆盖主错误的问题），同时移除流式命令确认子进程退出（`EXIT:`）后不可达的重复清理分支。
- **A3 双 Die 物理单元计数与实测空闲 HBM 归一化（`remote-dev #44`）**：`normalize_remote_probe_spec` 按可独立租约的物理执行单元（`dies`）统计 `npu_count` 与 `free_npus`（单张 Ascend 910C A3 双 Die 卡计为 `2` 个物理单元），在存在 `free_phy_ids` 时（含空列表 `[]`）以其为权威空闲物理单元集合；`vram_free_mb` 严格按非繁忙物理单元实测 `hbm_total_mb - hbm_used_mb` 计算，未观测到已用显存时绝不将总容量当作空闲显存，并显式返回 `vram_free_observed`。
- **准备作业状态刷新、HBM 遥测一致性与主机容量准入（`coordinator #63` / `#64`）**：
  - 修复 `service_gang.py` 遗漏 `preparation_control` 导入导致远端准备作业状态刷新误记为 `state="uncertain"` 的问题，并在状态观测与终态推进中恢复准备作业刷新与编译租约收尾。
  - `fleet_probe_parser.py` 在保持昇腾 950DT（A5）按进程表判定设备繁忙的同时，如实保留 `npu-smi info` 测得的 `hbm_used_mb` 用于显存余量计算；`parse_npu_smi_usages` 仅对单 Die 或整卡记录补充 `npu-smi info -t usages` 的整卡统计并由 `device_occupancy_inventory` 统一汇总卡/Die 空闲状态，防止整卡统计覆盖双 Die A3 卡。
  - 当角色声明 `cpu_cores`、`memory_mb` 或 `hbm_mb` 下限时，`ServiceEvidenceMixin._observe_host_specs` 通过 `_probe_host_record`（`probe_machine_record`）对候选主机采样生成 `host_specs` 快照，并在 `CoordinatorService` 的 Donor 挑选（先 `can_prepare` 再 `hardware_shortfall`）、用户容器开通（`hardware_shortfall`）、准备后复核与最终角色绑定复核（`runtime_matches`）中一致核对主机级实测余量（独立辅助函数 `select_runtimes(..., host_specs=...)` 亦支持 `host_specs`）；资源不足或未观测主机通过 `shortfall_reason` 返回按主机去重的缺口说明。
- **已验证测试事实**：在常驻 A2（`173.125.1.2`）与 A3（`192.168.13.165`、`192.168.13.154`）主机上执行只读 Fleet 容量探测（`test_live_fleet_probe_and_capacity_across_a2_and_a3`），实测 **`1 passed`（`8.01s`）**。

### 3. 诊断采集协作式排空与仿真算子实测画像计划（`diagnostics 0.5.2` & `sim 0.7.1` 候选）

- **诊断协作式摄取排空、离线阶段准入预算与记录边界游标保持（`diagnostics #29`）**：
  - 在 `ingest()` 既有的 `max_files=256`、`max_bytes=8 MiB` 与 `4096` 目录项上限基础上，新增 `cancel` 与单调时钟 `deadline` 协作式停止检查：触发时设置 `counts["limited"] = 1`，在完整 JSONL 记录边界退出并将最后一条已入队完整记录的字节 `offset` 写入 SQLite `cursors` 表供下一周期续扫（不宣称进程被强杀 `SIGKILL` 或崩溃时的 `exactly-once` 保证）。
  - 后台 Worker `run_cycle` 在 `cancel` 置位后保留本轮已收集数据，停止准入后续根目录 `ingest`、`prune` 与 `publish_one` 阶段，并返回 `status="degraded"`、`limited=1`。
  - `reporting maintain --budget-seconds` 是纯离线维护阶段（`"network": False`，不含诊断包构建、远端 GitHub 对账或 `POST`）；`budget_seconds`（默认 `75` 秒）作为阶段准入预算，在每个根目录 `ingest` 和 `prune` 前预留 `3.0` 秒 SQLite 结算窗口，预算不足时记录 `category="budget_exhausted"` 并降级为 `status="degraded"`（非操作系统级 20 秒停机保证或总耗时硬上界）。
  - 出站对账读取的有界化方案作为未实施后续设计单独记录于仓内 `docs/outbound-reconciliation-followup.md`，严格保持 `unknown` `POST` 绝不重放、GitHub 搜索未命中绝不等于远端不存在。
  - **验证与已知边界**：本地契约测试在 Python 3.11 与 3.13 下 **`132 passed`**。此前在 Windows 环境下曾出现过一次旧同意隔离测试预期摄取 2 条记录但实际摄取 1 条、随后重跑通过的现象，该偶发波动根因尚未查明，本次不宣称已根因修复。
- **实测算子画像计划、完成时间下界与声明工作量代理（`sim #16`）**：
  - `ProfiledKernelProvider`（`mindie_sim/profiled_kernel.py`，`backend="profiled_kernel"`）按显式配置的 `bindings`（要求 `binding["timing_scope"] == "profiled_device_kernel"`，且算子标识、`hardware_key`、`environment_key` 精确一致）只读查询 `mindie-profiler` SQLite 资产库的 `variants` 与 `costs` 表。
  - 生成单阶段 `ExecutionStage("captured_service", demands=demands, minimum_duration_ms=observation["median_ns"] / 1e6)`，将实测核函数耗时中位数作为单任务完成时间下界，同时保留算子声明的 `cube`/`vector`/`hbm`/`mte2`/`mte3` 工作量代理（未声明工作量的算子以 `profile_occupancy_undeclared_for_shared_stage` 拒绝，`independent_accuracy_acceptance=False`）。
  - 在 `a3_cost.py` 中，专用实测校准与通信拓扑模型保持原有定价优先级并记录 `superseded_profile_variant`，仅在自相矛盾声明（`PROFILE_VARIANT_CONTRADICTIONS`）或显式绑定的 `profile_variant` 缺失/被解析后端替换时抛出 `A3InputError`；已由 `profiled_kernel` 定价的算子标为 `calibration.status = "profiled_kernel_observed"`，并在 `a3_measurement.py` 的 `record_prediction_misses()` 中复用已有观测、跳过重复采样请求。
  - **已验证测试事实**：算子画像提供方定向测试 **`22 passed`**。

  - `.github/workflows/publish-product.yml` 与 `.github/scripts/collect_product_benchmarks.py` 新增明确的 `release-kind=patch` 路径：仅允许真正的维护补丁（`PATCH > 0` 且禁止传入历史 `value-suite-path`）走补丁发布门禁，功能里程碑版本仍强制走完整的 `milestone` 产品价值验收门禁。
  - 在 `release-kind=patch` 模式下，流水线不会将历史 `0.1.0` 价值报告重标为 `0.1.1` 新实验，但继续强制校验所有组件的真实正式 GitHub Release、不可变 Tag SHA、包版本、各仓 `mindie-release-benchmark/2` 报告与 SHA256 摘要，并强制校验 `channels/0.1.json` 与 `benchmark-manifest.json` 的组件集合、版本号与提交 SHA 完全一致（随发布资产输出 `release-channel.json` 并在 `product-release-provenance.json` 中记录 `channel_sha256`）。
  - `.github/workflows/publish-release.yml` 新增 `release-notes-path` 输入，支持各组件正式 Release 直接采用仓内审校定稿的社区版本说明（同时打包为 `release-notes.md` 并纳入 `SHA256SUMS`），不再默认以原始基准报告或自动生成的提交列表充当 Release Notes。
  - **已验证测试事实**：`mindie-bench #27` 已通过跨平台 CI 并合入（`484b80621aaf9293c559786d0ef2174c79a0dbb4`）；真实执行 Git Tag 前置检查与产物收集器的本地回归测试 **`30 passed`（`18.12s`）**。

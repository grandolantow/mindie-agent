# MindIE Agent `0.1.0` 版本发布说明（Milestone & `0.1` 演进通道）

[English](0.1.0.en.md) · [文档中心](../README.md) · [版本兼容与无感更新](../release-compatibility-and-update.md)

本文记录 MindIE Agent `0.1.0` 里程碑版本的核心架构更新、[`channels/0.1.json`](../../channels/0.1.json) 通道清单（Release Channel Manifest）机制、十二个配套代码仓库的精确源码清单，以及支持 `0.1.x`（`0.1.1`、`0.1.2`……）单组件独立热修与三层极速触达演进的完整规范。

从 `0.1.0` 起，MindIE Agent 正式引入 **`0.Y.0` 特性里程碑 + `0.Y.Z` 通道热修（Release Channel Manifest）** 的双层 SemVer 演进体系：
- **`0.Y.0`（如 `0.1.0` → `0.2.0`）**：代表包含重大新特性或跨组件协议演进的**里程碑版本（Milestone Release）**，提供完整版本发布说明（如本文 `docs/releases/0.1.0.md`）与十二仓全量基准验证；
- **`0.Y.Z`（如 `0.1.1`、`0.1.2`）**：代表由 [`channels/0.1.json`](../../channels/0.1.json)（`schema: "mindie-release-channel/1"`）驱动的**快速缺陷修复与单组件独立更新（Single-Component Hotfix）**。当底层单个共享组件（如 `remote-dev`、`diagnostics` 或 `knowledge`）发布缺陷修复时，只需更新通道清单中的组件版本与精确 Commit SHA 即可向全网客户端推送 `uv` 单包增量替换（空闲窗口原子切换 `< 500ms`），**无需重新打包并连坐重发 `mindie-agent-codex`、`mindie-agent-cc`、`mindie-agent-kimi` 与 `mindie-agent-dsh` 四个宿主插件**。

---

## 一、核心更新

1. **发布通道清单（[`channels/0.1.json`](../../channels/0.1.json)，`schema: "mindie-release-channel/1"`）与单组件解耦演进**：
   - 建立 `track: "0.1"` 通道清单，统一声明 `milestone_version: "0.1.0"`、`current_patch_version: "0.1.0"`、十二个代码仓库的精确版本/Tag/Commit SHA 以及组件级更新策略（`independent_update_allowed: true`、`hotfix_trigger_on_error: true`、`etag_poll_interval_sec: 3600`、`background_poll_interval_sec: 86400`）；
   - 解耦底层共享组件与四个宿主插件的发版绑定：在 `0.1.x` 补丁周期内，单组件修复直接通过 `channels/0.1.json` 演进（`0.1.0` → `0.1.1` → `0.1.2`），彻底消除“改一行底层组件代码需串行重发 4 个宿主插件 Release”的发版摩擦。
2. **单组件独立增量更新（`< 500ms` 空闲窗口原子切换）**：
   - 当 `channels/0.1.json` 中仅单个或少数共享组件（如 `diagnostics` 或 `remote-dev`）版本发生变更时，本地更新器在后台基于 `uv` 缓存执行单包增量替换，并在服务空闲窗口内以 `< 500ms` 完成排他锁原子绑定切换，不中断任何在途会话。
3. **三层极速更新触达机制（Three-Tier Rapid Rollout）**：
   - **(a) 故障/崩溃触发的即时自愈检查（Fault/Crash-Triggered Immediate Self-Healing）**：当 `diagnostics` 或任意 MCP 工具在执行中遭遇非预期异常/崩溃时（`hotfix_trigger_on_error: true`），后台立即旁路 `24 小时`（`86400s`）常规冷却周期，异步拉取 `channels/0.1.json` 检查是否存在针对该故障组件的 `0.1.x` 热修补丁并完成自愈升级；
   - **(b) 轻量级 HTTP `ETag` 通道轮询（Lightweight HTTP `ETag` Channel Polling）**：按 `etag_poll_interval_sec: 3600`（1 小时）携带 `If-None-Match` 发起极轻量级通道元数据探针，未变更时服务端直接返回 `304 Not Modified`（零载荷解析开销），常规全量回退轮询周期保持 `background_poll_interval_sec: 86400`（24 小时）；
   - **(c) 零代码知识与规则流热加载（Zero-Code Knowledge/Rule Feed Hot-Reload）**：7 大昇腾公共知识库与分诊规则（`L1–L4` 知识单元）通过 `feed_sync` 持续增量同步与就地热加载，无需触发代码包重装或进程重启。
4. **全量继承并固化 `0.0.3` 十二仓实测能力基线**：
   - 包含 `knowledge v0.13.0`（L1–L4 渐进式披露与 `< 8,000` tokens 预算门控）、`profiler v0.5.0`（`msprof` 毫秒级就地只读慢卡/慢链路与显存归因）、`sim v0.7.0`（A2/A3/A5 四层 Roofline 与算子流水仿真）、`diagnostics v0.5.1`（CANN/`plog` 确定性根因分诊与双层隐私脱敏）、`coordinator v0.6.2`（多 Agent 选卡/端口租约防冲突与 A5 拓扑预检）、`npu-top v0.2.1` 及 `remote-dev v0.10.4`。

## 三、`0.1.0` → `0.1.1` 单组件热修工作流与基准证据

- **十二仓基准与价值实测证据**：见 [`0.0.3` 实测证据说明](0.0.3.md#三各组件价值验证与实测证据)、[`component-value-results.md`](0.0.3/component-value-results.md) 与 [`benchmark-results.md`](0.0.3/benchmark-results.md)。
- **从 `0.1.0` 升级至 `0.1.1` / `0.1.2` 的标准流程**：
  1. 维护者在目标组件仓（如 `mindie-agent/diagnostics` 或 `mindie-agent/remote-dev`）发布新版本 Tag 并通过单仓 `mindie-bench` 发布门禁；
  2. 在主仓库 [`channels/0.1.json`](../../channels/0.1.json) 中将 `current_patch_version` 递增为 `"0.1.1"`，仅更新对应组件的 `version`、`tag` 与 `commit`/`revision`，并在 `patch_releases` 中追加变更摘要；
  3. 已安装的四个宿主插件通过 HTTP `ETag` 轮询（`3600s`）或异常触发自愈检查（`hotfix_trigger_on_error: true`）感知 `channels/0.1.json` 更新，在后台完成单包 `uv` 增量替换并在 `< 500ms` 空闲窗口内原子切换生效。

# MindIE Agent `0.0.2` Release Record

[中文](0.0.2.md) · [Documentation index](../README.en.md)

This is a release candidate record. The formal GitHub Release and exact source manifest determine publication status.

The product and the Codex, Claude Code, Kimi Code, and DSH plugins all use `0.0.2`. Shared components keep independent version sequences. The public `mindie-bench` code repository uses `0.2.0`. This release focuses on business correctness after the refactor, exact installed dependencies, and benchmark delivery with every release.

## Changes

- **Remote execution and coordination:** durable job controls, handshakes, and multistage SSH diagnostics share a bounded call budget. Submissions read current Git identity rather than cached source identity. Completed remote results remain intact; failures and uncertain external writes remain explicit.
- **Knowledge and consent:** fixes cover consent migration, Windows DPAPI context protection, and concurrent consent updates. Previously published fixes for background service ownership, task retirement, and Git resolution remain included.
- **Unified contribution and fault reporting:** one contribution choice controls knowledge sharing and product fault reports. DSH's mismatched reporting path is corrected. Recording, ingestion, and sending check the same consent revision; enabling prepares the native service, and disabling stops both outgoing paths. Temporary GitHub failures do not permanently discard unsent faults.
- **Host process boundaries:** summary calls budget identity checks, model execution, and cleanup separately. DSH setup drains real process trees on timeout, preserves unknown usage, and removes retry paths that deleted configuration to hide errors.
- **Windows installation:** Codex shortens new runtime directory identifiers while keeping the full identity in the receipt, fixing dependency paths that exceeded traditional Windows limits under the default user layout. Native Windows Kimi requires Python 3.12 or later; setup prefers 3.13.
- **Shared state ownership:** the three plugin diagnostic fallbacks and Kimi's duplicated consent bootstrap are removed. Shared runtime failures remain explicit, without changing saved consent or replacing the original business result.
- **Cold startup and updates:** Claude Code serializes initial state preparation and no longer makes ready MCP servers wait on optional maintenance's exclusive lock. Maintenance timeouts remain visible. Kimi uses the shared selector for formal releases, host compatibility, and exact tag identity. DSH installs its summary worker in persistent data storage so removing the setup checkout does not break it.
- **Linux benchmark sandbox:** uv aliases for the same authorized Python runtime work inside the sandbox while unauthorized files and host loopback remain isolated. Unix gateway tests exercise the actual relay.

### Real Fault Reporting Through the Unified Switch

An isolated profile installed Knowledge `4e32830` and diagnostics `1b5a0ee` noneditably from their exact Git commits. After explicitly enabling contribution, the native macOS launchd reporter automatically created public synthetic [Issue #243](https://github.com/mindie-agent/mindie-agent/issues/243). The background worker performed the external write; the acceptance script did not submit an Issue on its behalf.

Readback confirmed diagnostics `0.4.3` and its full commit SHA, with the private sentinel, raw error text, and local directory excluded. The same worker consumed a duplicate fault while the durable queue retained one published incident. Faults recorded before enabling and after disabling carried no upload authorization. Disabling invalidates the choice used by both knowledge contribution and diagnostics publication. The isolated native service was removed and confirmed absent afterward.

The first deduplication check in the acceptance script used `incident_id` where the stored event uses `operation_id`. After correcting the check, verification continued on the existing queue without replaying a completed external write. The fixture failure and the successful product delivery remain separate evidence.

On Windows 4090, an ordinary desktop token (`TokenElevation=0`) started the exact same installed runtime through Task Scheduler. Its background worker consumed the matching public synthetic fault and reconciled it to Issue #243 through a read-only GitHub lookup, without creating another Issue.

Existing `disabled`, `later`, and `read-only` choices stay off. A legacy knowledge-only `contribute` choice without a unified authorization revision does not silently gain diagnostics permission during upgrade; one explicit enable through the same contribution entry applies the new shared choice. Configuration and worker readiness are reported separately, and authentication, network, or startup failures cannot appear as successful delivery. Disabling prevents subsequent sends; it does not undo earlier completed public writes.

## Benchmarks with Every Release

Each code repository's tag workflow checks source and versions, installs actual dependencies, validates first-party formal releases, runs local contracts and benchmarks, builds artifacts, and verifies checksums. A failed, missing, or uncertain required case blocks publication.

Component releases include `benchmark-results.json`, `benchmark-results.md`, `benchmark-SHA256SUMS`, and a `SHA256SUMS` covering all public assets. The product includes aggregated results, the manifest, and `product-release-provenance.json`. Private logs and user conversations are excluded.

The first diagnostics, remote-dev, and npu-top checksum lists included a build-only `.gitignore` that was not uploaded. Only `SHA256SUMS` was corrected, with a disclosure in each release. Tags, packages, benchmark reports, and their digests were unchanged. The shared publisher now excludes hidden build files.

The Knowledge `v0.12.0` and coordinator `v0.5.0` candidates were blocked by a benchmark data contract and an optional Python test extension, respectively. Both tags remain without formal Releases. The fixes first shipped as `v0.12.1` and `v0.5.1`; the final unified contribution combination advances to `v0.12.2` and `v0.5.2`. Failed candidate tags were not moved or relabeled as passing.

## DSH Same-Version Update

DSH remains at `0.0.2` by product decision. Its previous `0.0.2` source was `828c375d1f546ed653250526465b8075c1691390`; the manifest identifies this release's paired source.

The old updater only selects a version greater than the installed version. Existing installations of the old `0.0.2` therefore require an explicit one-time refresh of both the runtime and the DSH plugin bundle, followed by restarting the entire DSH process. Existing consent and knowledge data are retained. The [same-version refresh guide](https://github.com/mindie-agent/mindie-agent-dsh/blob/main/docs/same-version-refresh.md) uses an exact source SHA to avoid client caches for the unchanged tag name. Subsequent higher versions use the normal updater.

## Known Boundaries

- Application control on the Lenovo Windows acceptance machine blocked `pythonw.exe` with WinError 4551. No machine policy was changed or bypassed. Background capture on that machine is not counted as passed.
- Ordinary Windows desktop tokens were validated. An elevated host may create private state directories that its ordinary-user background task cannot read. Mixed elevated-host and ordinary-task execution is not declared supported; ACL changes or elevation were not used to bypass this boundary.
- Source tests, partial native host acceptance, live NPU integration, and CPU baselines are separate evidence. The previous release's complete host matrix is not relabeled as fresh `0.0.2` acceptance.
- Isolated productivity benefits require controlled tasks and environments. This release provides reproducible baselines and recurring release reports.
